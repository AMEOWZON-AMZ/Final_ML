# Final_ML

`Final_ML`은 **냥냥 편지** 서비스의 ML 영역을 한 곳에서 관리하기 위한 통합 문서/운영 저장소입니다.  
현재 문서는 아래 두 축을 중심으로 구성됩니다.

1. **data-status-ml**: 사용자 상태 데이터 기반 이상 탐지/스코어링
2. **vc-ml**: 사용자 상태를 반영한 음성(보이스/BGM) 생성·변환 파이프라인

> 이전 버전이 개요 위주였다면, 이번 문서는 실제 운영 관점(입력/출력, 파이프라인, 평가, 연동 방식, 배포 체크리스트)까지 포함해 확장했습니다.

## 1. 프로젝트 개요

### 1.1 문제 정의

냥냥 편지의 ML 목표는 크게 두 가지입니다.

- 사용자의 **상태 변화(행동 패턴 이상)** 를 정량적으로 감지한다.
- 감지된 상태를 바탕으로 **정서적으로 맞춤화된 오디오 경험** 을 제공한다.

즉, “상태를 읽는 모델”과 “상태를 표현하는 모델”을 결합해 개인화 루프를 구성합니다.

### 1.2 구성 요소

| 구성 | 역할 | 주요 출력 |
|---|---|---|
| data-status-ml | 상태 이상 탐지 및 점수화 | anomaly score, risk label |
| vc-ml | 상태 기반 음성/보이스 스타일 변환 | transformed audio, metadata |

## 2. data-status-ml

사용자의 일별/구간별 행동 데이터를 바탕으로 **정상 패턴 대비 이탈 정도** 를 계산하는 파트입니다.

### 2.1 목표

- 개별 사용자 기준 정상 분포를 학습
- 이상 가능성이 높은 시점을 조기 포착
- 상위 서비스가 활용 가능한 점수(스칼라) 및 레이블(구간) 제공

### 2.2 핵심 모델

- **Isolation Forest** 기반 이상 탐지
  - 지도 라벨이 충분하지 않은 환경에서 실용적
  - 상대적으로 빠른 학습/추론
  - 점수 임계치 조정으로 서비스 정책 반영 용이

### 2.3 입력 데이터(예시)

- 일별 활동량/행동 빈도
- 시간대별 사용 패턴 통계
- 연속성/변동성 지표(rolling mean/std 등)
- 결측/이상치 처리 후 피처 벡터

### 2.4 전처리 파이프라인(권장)

1. raw 로그 수집 및 기간 정렬
2. 결측치 보정(0 대체/보간/구간 제거 정책)
3. 사용자 단위 표준화 혹은 글로벌 스케일링
4. 피처 엔지니어링(추세/변동/주기성)
5. 학습·검증 구간 분리

### 2.5 출력 스펙(권장)

- `anomaly_score` (float): 값이 클수록 이상 가능성 높음
- `risk_band` (enum): `normal`, `watch`, `high` 등 구간화 결과
- `feature_snapshot` (json): 설명 가능한 주요 피처 값
- `timestamp` / `user_id`

### 2.6 평가 지표(운영형)

라벨 유무에 따라 다르게 봅니다.

- 라벨 없음: 점수 분포 안정성, drift 감지, 상위 n% 알람의 운영 적중률
- 라벨 있음: PR-AUC, ROC-AUC, Recall@K, 임계치별 F1

### 2.7 운영 시 주의점

- 사용자 집단 변화(신규 유입/시즌성)에 따른 score drift 모니터링
- 단일 임계치 고정보다 서비스 상황에 따른 동적 임계치 전략 고려
- 설명 가능성(어떤 피처가 이상에 기여했는지) 로그화

## 3. vc-ml

사용자 상태(감정/분위기/리스크 밴드)를 반영해 **보이스 또는 BGM 톤을 변환/생성** 하는 파트입니다.

### 3.1 목표

- 상태 컨텍스트에 맞는 음색/톤/무드 반영
- 사용자에게 자연스럽고 일관된 오디오 경험 제공
- 상위 서비스가 즉시 재생 가능한 산출물 전달

### 3.2 핵심 모델

- **Seed-VC** 기반 Voice Conversion 파이프라인
  - 입력 음성과 목표 스타일 특성을 결합
  - 상태 라벨 기반 스타일 프롬프트/조건 제어 가능

### 3.3 입력(예시)

- 소스 오디오(보이스 혹은 베이스 BGM stem)
- 목표 상태 라벨(`calm`, `focus`, `comfort`, `alert` 등)
- 후처리 옵션(샘플레이트, 노멀라이즈, 길이 정합)

### 3.4 처리 단계(권장)

1. 오디오 로드 및 포맷 정규화
2. 상태 기반 스타일 조건 생성
3. Seed-VC 추론 수행
4. 후처리(노이즈/볼륨/클리핑 보정)
5. 메타데이터와 함께 저장

### 3.5 출력 스펙(권장)

- `audio_path` 또는 binary blob
- `sample_rate`, `duration_sec`, `loudness`
- `style_tag`, `model_version`, `inference_time_ms`

### 3.6 품질 평가(권장)

- 객관 지표: loudness consistency, clipping ratio, duration alignment
- 주관 지표: MOS(자연스러움), 스타일 적합도, 이질감 여부
- 서비스 지표: 재생 완료율, 재청취율, 스킵률 변화

### 3.7 운영 시 주의점

- 과도한 변조로 인한 부자연스러움 방지(강도 상한)
- 샘플레이트/코덱 불일치로 인한 품질 저하 방지
- 모델 버전별 출력 편차 추적 및 롤백 전략 확보

## 4. 두 시스템 통합 아키텍처

### 4.1 End-to-End 흐름

1. 사용자 로그/상태 데이터 수집
2. `data-status-ml`이 이상 점수 및 위험 구간 산출
3. 점수/레이블을 오디오 스타일 정책으로 매핑
4. `vc-ml`이 스타일 반영 오디오 생성
5. 앱/서비스에 전달 및 사용자 반응 로그 재수집

### 4.2 정책 매핑 예시

| anomaly/risk | 오디오 정책 예시 |
|---|---|
| normal | 기본 톤 유지, 변환 강도 낮음 |
| watch | 안정감 있는 톤/무드로 완만한 변환 |
| high | 자극 완화 중심 톤, 안내성 음성 강조 |

### 4.3 피드백 루프

- 사용자 반응(재생 시간, 스킵, 만족도)을 다시 상태 모델/오디오 정책 개선에 반영
- 일정 주기로 임계치·스타일 정책 재학습/재튜닝
